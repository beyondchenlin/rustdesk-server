## 第一轮：问题定位与修复

### 1. 本地管理客户端接受录制的服务端认证会话

原有管理通道的服务端随机挑战有认证码，但没有绑定当前客户端随机数。假冒的本地服务可以重放此前有效的服务端挑战和返回消息，使管理客户端把旧状态或旧操作结果视为当前结果。该问题不能让没有凭据的攻击者生成新的有效管理员命令，但能破坏客户端对管理结果的新鲜性判断。

先加入回归用例 `client_rejects_replayed_server_challenge_and_reply`。修复前运行得到退出码 **101**，明确失败信息为 `replayed server transcript was accepted`（重放的服务端会话被接受）。随后加入 32 字节客户端随机数，并将其绑定到服务端挑战认证码。相同用例在最终全仓测试中通过。

变更文件：`src/managed_relay_admin.rs`。
本地管理帧前缀及认证域由 `BKREL1`（旧管理协议）升级为 `BKREL2`（新管理协议）。部署时设备识别服务和管理工具必须作为同一套版本升级；不提供旧认证回退。原生远控协议和命令行参数没有改变。

### 2. 空中继结果被原生客户端回退绕过

原生客户端会把空中继地址回退为设备识别主机的相邻端口。只把托管池的选择结果置空，不能阻止客户端继续尝试池外或已不健康的旧节点。服务端原有处理还会转发对端提交的中继地址。

修复后，托管模式下的新中继请求和初始中继响应均须通过当前健康快照的精确端点许可判断；无效端点使用既有原生错误字段返回 `Managed relay unavailable`（托管中继暂不可用）。直连协商仍保留真实地址，只移除不许可的中继候选，因此中继全故障不阻断能够建立的直连。

变更文件：`src/managed_relay_runtime.rs`、`src/rendezvous_server.rs`。`src/relay_server.rs` 仅增加针对许可判断的测试断言；没有修改已建立中继会话的数据转发逻辑。未启用托管池时保留原版路径。

边界：这项授权控制约束设备识别服务的新连接协商，不声称撤销一个已经知道旧中继端点及协议参数的独立直连中继流。旧会话连续性由真实数据传输验证，未把“旧节点还在运行”误报为当前配置健康。

### 3. 全故障状态缺少明确告警日志

原有健康刷新在探测完成且全部失败时仍正常返回，只更新状态，外层错误日志不会触发。现增加健康状态转换日志：全不可用为错误、部分降级为警告、恢复健康为信息。实际双节点全故障测试同时核验空候选、原生拒绝及服务端告警内容。

变更文件：`src/managed_relay_runtime.rs`。

### 4. 数据库压力测试的隔离及任务错误传播

原有测试使用仓库目录下固定的 `test.sqlite3`，并丢弃并发任务的返回错误。重复执行会受到前一次数据影响，子任务失败也不能可靠传递给测试主任务。

现在使用独立临时目录，并逐项验证并发任务结果。保留原有 10,000 次插入和 10,000 次查询，未降低测试规模；没有修改生产数据库访问逻辑。

变更文件：`src/database.rs` 的测试模块。既有 `db_v2.sqlite3` 的文件哈希在测试及构建前后完全一致。
